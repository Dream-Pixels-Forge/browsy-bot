# v1.0.0 — Cookie/Storage management + 1.0 release

## Objective
Add cookie and storage management so browsy-bot can maintain authenticated
sessions across captures (login once, reuse cookies), plus ship the 1.0.0
release (semver tag, changelog, README, publish).

## Context
browsy-bot has no way to persist login/auth state. Every capture starts
fresh, which blocks real E2E flows (logged-in dashboards, checkout flows,
etc.). CDP's Network and Storage domains let us get/set/delete cookies and
inspect local/session storage — the missing piece for production E2E.

## Deliverables
- [x] `src/core/cookies.ts` — `getCookies(session)` / `setCookies(session, cookies[])` / `deleteCookies(session, names[])`:
      `Network.getCookies`, `Network.setCookies`, `Network.deleteCookies`
- [x] `src/core/storage.ts` — `getStorage(session, origin)`:
      `Runtime.evaluate` reading localStorage/sessionStorage per origin
- [x] `src/core/actions.ts` — wire cookies/storage into public surface
- [x] `src/mcp.ts` — `browsy_get_cookies`, `browsy_set_cookies`, `browsy_delete_cookies`, `browsy_get_storage` tools
- [x] `src/cli.ts` — `browsy get-cookies`, `browsy set-cookies`, `browsy delete-cookies`, `browsy get-storage` commands
- [x] Tests: test/cookies.test.ts, test/storage.test.ts, tools in mcp.test.ts
- [x] Release: semver tag v1.0.0, changelog, README update, publish to npm
- [x] Done when: `npm run typecheck && npm run build && npm test` all green + release published

## Risks
- Cookies are domain-scoped; `setCookies` requires matching domain/path or they're silently dropped.
- `Storage.getCookies` is not a real CDP method — use `DOM.getCookies` (deprecated but works) or evaluate `localStorage` via Runtime.evaluate as fallback.
- HttpOnly cookies can't be read via JS evaluation but CAN via `Network.getCookies` (CDP has full access).
