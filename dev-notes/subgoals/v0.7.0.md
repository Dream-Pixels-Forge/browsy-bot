# v0.7.0 — Performance metrics & error budget

## Objective
Give browsy-bot performance measurement so it can tell users *how fast* a page
is and *why* it's slow — Core Web Vitals (LCP, CLS, INP), navigation/resource
timing, and a console error budget that can fail CI.

## Context
browsy-bot can drive, capture, and validate UI, but it has no performance
surface. Adding performance metrics lets teams use browsy-bot for performance
regression detection alongside visual regression (v0.4.0).

## Deliverables
- [x] `src/core/performance.ts` — `getPerformanceMetrics(session)`:
      `Performance.enable` + `Performance.getMetrics`, returns structured
      metrics map. Expose `browsy_performance` tool.
- [x] `src/core/perf-budget.ts` — `checkPerformanceBudget(metrics, budget)`:
      compare metrics against thresholds, return pass/fail + violations.
- [x] `src/core/actions.ts` — wire `getPerformanceMetrics` into public surface.
- [x] `src/mcp.ts` — `browsy_performance` tool returning metrics JSON.
- [x] `src/cli.ts` — `browsy performance` command.
- [x] Tests: test/performance.test.ts, test/perf-budget.test.ts,
      browsy_performance in mcp.test.ts.
- [x] Done when: `npm run typecheck && npm run build && npm test` all green.

## Risks
- Performance metrics require `Performance.enable` before page load to be
  accurate; callers must enable early. Document this clearly.
- LCP/CLS/INP are "best-effort" via Performance.getMetrics — may be 0 if not
  measured yet. Document as approximate.
- Budget thresholds are user-provided; no defaults enforced.
