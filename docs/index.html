Why browsy-bot

The raw protocol, with zero in the way.

Every call gets an explicit browserUrl and optional targetId — no hidden driver state, no extra binaries. These are the pillars.

Zero middleware

No ChromeDriver, Puppeteer, or Playwright. A direct CDP WebSocket — minimal latency, full protocol fidelity, deterministic lifecycle.

Zero hidden state

Addressed explicitly per call. Sessions are cached when you want them, torn down when you don't — you always know what's connected.

Granular targeting

Operate on specific tabs and windows via targetId, or auto-discover the first page target. Full multi-tab control.

Protocol-complete

Domain wrappers for Page, Runtime, Performance, Accessibility, and Target — the CDP surface you actually need, typed.

Multi-tool

One core, three adapters: an OpenCode plugin, a universal MCP server, and a CLI — all built on the same typed CDP client.

Learns across sessions

Optional memorius integration stores selectors, quirks, and navigation flows — and surfaces them before the next task.

v0.2.0 toolkit

Primitives that remove the tedious parts.

Beyond raw CDP, browsy-bot ships a small toolkit that covers the jobs people actually automate — diagnostics, data pulls, browser lifecycle, and real input events.

doctor

Read-only diagnostics

Probes the CDP endpoint, target count, browser-binary discovery, and memorius availability, then returns an actionable report with next-step suggestions. The first thing to run when nothing works.

browsy doctor --json
# not ready: CDP endpoint unreachable. Launch Chrome with:
#   chrom… --headless --no-sandbox, or run "browsy ensure-browser".

extract

Structured data pull

Pulls typed records from matching elements in a single in-page script — no bespoke evaluate boilerplate. Field specs: text, html, value, or attr:<name>.

browsy extract "article.card" text "attr:src" value
# → [ { "text": "...", "src": "..." }, ... ]

ensure-browser · stop-browser

Self-service lifecycle

ensure-browser probes the endpoint and, if it's down, spawns a Chrome/Chromium on a dedicated profile dir (never your logged-in one), writes a pidfile, and waits for CDP to answer. stop-browser SIGTERMs the recorded pid.

browsy ensure-browser --port 9222 --no-headless
browsy stop-browser

--trusted input

Renderer-trusted events

click and fill gain an opt-in --trusted flag that dispatches renderer-trusted CDP input events (Input.dispatchMouseEvent / Input.insertText) instead of JS-dispatched ones — so the page sees a real user event.

browsy click ".save" --trusted
browsy fill "#email" "a@b.c" --trusted
Get started

From zero to a driven tab in three lines.

As a standalone library there is no build step on the consumer side — import, connect, act.

import { getSession, navigatePage, click, extract } from "browsy-bot";

const s = await getSession("ws://localhost:9222");
await navigatePage(s, "https://example.com");
await click(s, ".save", { trusted: true });
const rows = await extract(s, "article.card", ["text", "value"]);
  1. 01Point it at a browser. Start Chrome with remote debugging, or let browsy ensure-browser start a dedicated one for you.
  2. 02Get a session. getSession(browserUrl, { targetId? }) returns a cached CDP socket keyed by endpoint + tab.
  3. 03Act. Navigate, click, fill, extract, capture console and network — all over the same session.
Operating notes

CDP is a powerful channel. Know the blast radius.

A live endpoint is equivalent to a shell on the machine that runs Chrome. Here's the posture.

  • Loopback only. The default is ws://localhost:9222. Don't bind the CDP port to 0.0.0.0 unless it's behind a firewall and you own the blast radius.
  • Profile-scoped launch. ensure-browser only ever starts a browser on a dedicated user-data-dir — never your logged-in profile. If you want a logged-in browser, launch it yourself and point -u at it.
  • --trusted is still JS-gated. The trusted path measures an element's rect in-page then dispatches input events at that coordinate. A page can move the target between measure and dispatch; "trusted" means the listener sees a user-originated event, not a synthetic el.click().
  • Memorius learns persist. Learnings live on disk; if the vault is shared, learned selectors and flows become information to other agents on the host. Use a per-user or per-project vault.
